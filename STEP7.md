# Шаг 7. Просмотр попытки и первого неверного события

Выбран локальный **JSONL** для обоих режимов. Рассмотрены также Langfuse и
Phoenix; внешнее хранилище этому стенду пока не требуется. Рабочие события
остаются в SQLite, исходные JSON-отчёты совместимы с экспериментальными командами.
JSONL — единое представление этих отчётов. Просмотр и экспорт не обращаются к сети.

## Полная попытка одной командой

Реальная неудачная попытка неполного заказа:

```sh
.venv/bin/python -m email_router.tracing \
  --report artifacts/live-source-boundary-20261019T193947383517Z/missing_shipping.json \
  --run-id run-80e0524c6e814d1d
```

Показываются письмо, конфигурация, все события в исходном порядке и снимок
сохранённых эффектов. Чтобы показать только первое неверное событие,
к той же команде добавить `--event-index 9`.

Для сохранения добавить `--output путь/новый-файл.jsonl`: существующий файл
не заменяется, родительская папка должна существовать. Неверный run_id, индекс
или формат возвращают код 2 без вывода фрагментов повреждённого входа.
Команда читает JSON, SQLite не открывает и исходный файл не меняет.

## Метаданные новых запусков

- `run_id` уникален для попытки в свежей базе. Повтор события в прежней базе
  остаётся возобновлением. Экспериментальные команды создают новые базы.
  `case_id` — ID письма; варианты окружения различаются версией данных.
- В каждой строке есть версии промпта и инструментов, хеши модулей кода,
  исходного состояния данных и конфигурации моделей. Данные хешируются до
  исполнения, включая тестовые изменения. Снимок конфигурации содержит роли,
  параметры генерации, интервал запросов и имитационные сбои.
- `event_index` задаёт порядок в попытке. Строки input_snapshot,
  run_config_snapshot и effects_snapshot имеют индекс null: это снимки,
  не дополнительные события исполнения.
- input_snapshot берётся из сохранённого run_start, а не из изменяемой записи
  письма. snapshot_source=run_start означает зафиксированный вход. Если старый
  отчёт не содержит run_start, используется доступный снимок отчёта с меткой
  available_report_message: его нельзя считать доказательством исходного входа.
  При ограничении экспорта сохраняются только служебные ссылки, источник
  обозначается run_start_redacted и snapshot_redacted=true. Изменение текста
  или классификации письма после обработки не восстанавливает критическое
  содержимое первоначального входа.
- model_request связан с model_response/model_error через `call_id`.
  Роли — extractor и planner; у workflow только extractor. Запрошенная модель
  записана до обращения, фактическая — в ответе. ID модели — доступная версия
  API, а не неизвестная точная версия весов.
- tool_request связан с результатом tool или tool_error через `call_id`.
  `provider_call_id` связывает вызов агента с предложенным моделью tool call.
  У действий, выбранных кодом workflow, он null. Каждый физический повтор
  чтения имеет отдельный call_id.
- Записаны начало, конец и duration_seconds. Длительность измеряется
  монотонными часами; для модели включает паузу клиентского ограничителя частоты.
  Токены — usage из ответа провайдера; отсутствующий расход не заменяется нулём.
- Прерванный вызов остаётся запросом без результата: завершение не выдумывается.
  Все инструменты сейчас сериализованы, параллельного выполнения нет.
  Обычные исключения получения/разбора ответа, включая JSONDecodeError,
  фиксируются связанным model_error с окончанием и длительностью, затем
  исключение выбрасывается повторно. Для неожиданных исключений записывается
  только безопасный тип и фиксированное пояснение; тело ответа и текст
  исключения не копируются в model_error или аварийный ручной разбор.
  KeyboardInterrupt/SystemExit не превращаются в завершённый model_error.

Эти поля не передаются модели и не меняют бизнес-правила. Для рабочей SQLite
добавлен events.metadata; открытие старой базы Store выполняет совместимую
миграцию с сохранением строк. Просмотр исторического JSON этой миграции не делает.
Старые отчёты не переписываются: неизвестные call_id, длительности и версии
в JSONL остаются null. Записанные исторические версии и ID модели сохраняются.

## Первое неверное событие

Попытка `run-80e0524c6e814d1d`, Gemini, до исправления:

| Событие | Что произошло | Вывод |
|---:|---|---|
| 9 | get_order вернул found для C-21/O-52 без shipping_status в data | Первое неверное событие: нарушен контракт ответа источника |
| 17 | controller_error: shipping_status | Следствие использования отсутствующего обязательного поля |
| Завершение | failed, аварийный unsupported_case | Неуспех по заранее записанному ожиданию управляемого ручного разбора |

Выбрано исправление на границе источника: проверять обязательные статусы до
выдачи found, возвращать source_data_incomplete с missing_fields и data=null,
не повторять неполный ответ как временный таймаут. Значения из письма не подставлять.
Подробности до/после и реальный успешный повтор — в [STEP5.md](STEP5.md).
На шаге 8 изменение нужно проверить на всём регрессионном наборе.
JSONL-выгрузка старого запуска не является новым сравнением моделей.

## Проверки и артефакты

88 автотестов прошли: три повтора в обоих режимах, ID и версии, пары вызовов,
изменение отпечатка данных, HTTP-ошибка, исключение инструмента, прерывание,
ID повторов, старые отчёты, отказ перезаписи JSONL и редактирование критического
содержимого. Для несинтетического письма применяется staff-only проекция.
Содержимое run_start и полные эффекты не возвращаются в экспорт; произвольные
дополнения к отчёту, например experiment, не копируются.
Также проверены изменение письма после запуска, обе стороны изменения его
классификации, безопасная регистрация ошибок парсинга и повторное выбрасывание
неожиданного исключения после записи model_error.

Новые локальные примеры явно используют подстановку, **не реальную LLM**:

- `artifacts/offline-source-boundary-20261019T195536151949Z`: первый агентный запуск после добавления метаданных, 2/2.
- `artifacts/offline-source-boundary-20261019T195646169067Z`: агент, 2/2.
- `artifacts/offline-source-boundary-20261019T195646281803Z`: workflow, 2/2.

JSONL-проекции реальной исторической неудачи и последних четырёх локальных
отчётов обоих режимов: `artifacts/trace-review-20261019T195742436307Z/manifest.json`.
Манифест содержит пути, run_id, хеши исходных отчётов и признак live_model.
Исходники отчётов проверены на неизменность. Первоначальная подготовка выполнялась
без API. Затем пользователь выполнил реальный Gemini-прогон после исправлений
по ревью: `artifacts/live-source-boundary-20261019T200719751593Z`, **2/2**.

| Кейс | run_id | Событий | Вызовов модели | Токены | Отклонений |
|---|---|---:|---:|---:|---:|
| complete_order | run-61e4725ce0154e59 | 24 | 5 | 13075 | 0 |
| missing_shipping | run-d24b9f59a77c4ef0 | 21 | 4 | 9512 | 0 |

В обеих трассах проверены пары call_id, длительности, порядок, версии и
равенство input_snapshot сохранённому run_start. Фактические эффекты сверены
с SQLite. Полный заказ назначен обработке заказов; неполный дал
source_data_incomplete с missing_fields=[shipping_status] и передан сотруднику,
без исходящего и controller_error. Указанные количества относятся к событиям;
три дополнительных JSONL-строки снимков в них не включены.
Рядом сохранены `complete_order.jsonl` и `missing_shipping.jsonl`.

Посмотреть новую полную попытку:

```sh
.venv/bin/python -m email_router.tracing \
  --report artifacts/live-source-boundary-20261019T200719751593Z/missing_shipping.json \
  --run-id run-d24b9f59a77c4ef0
```

Этот прогон подтверждает регистрацию успешных вызовов Gemini. Изменение письма
после обработки и некорректный JSON провайдера проверяются отрицательными
автотестами: обычный успешный ответ эти сценарии не воспроизводит.

Теперь одной командой можно получить попытку и показать первое неверное событие.
