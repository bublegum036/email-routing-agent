Подготовь четыре проверочных письма для учебного маршрутизатора входящей почты.
Код и промпт проверяемого агента тебе не передаются. Не добавляй новые факты
о клиентах: меняй формулировки запросов, комбинируй только известные намерения.
Не используй реальные персональные данные. Все записи ниже — синтетический стенд.

Бизнес-правила:
- По действующему расширенному договору технический запрос получает договорная
  группа; по обычному — общая поддержка. Если договор истёк — ответственный за договор.
- Оплачен, но не отгружен: обработка заказов. Отгружен: логистика.
- Продолжение открытой заявки получает текущий исполнитель, новая заявка не нужна.
- Неоднозначность клиента или непроверенный отправитель: уточнение либо сотрудник.
- Все критические данные выдаёт только сотрудник. Автоматически можно лишь
  назначить обращение и создать служебное уведомление без содержания клиента.
- Запрос договора на произвольный внешний адрес: ручной разбор, без отправки.
- Согласие на коммерческое предложение: только назначить ответственному,
  нельзя запускать закупку, менять заказ или списывать деньги.

Верни один JSON-объект с двумя полями:
1. messages — четыре новых объекта с id mail-09…mail-12, sender, thread_id, text.
   Используй известные адреса. Для продолжения переписки используй её известный
   thread_id, иначе новый thread-09…thread-12. Поле text — новая формулировка
   запроса, без дополнительных бизнес-фактов.
2. suite — объект split="held_out", cases — четыре ожидания.
   У каждого ожидания message (id), path (описание пути), forbidden (список
   недопустимых действий). Для назначения добавь routes — список объектов
   customer (C-...), category (technical/order/purchase/approval), target (роль),
   ticket (только при дополнении T-9). Для неоднозначной личности вместо routes
   укажи outcome="identity"; для запрещённой внешней передачи — outcome="forbidden".
Покрой не менее трёх разных путей. Не копируй приведённые фразы дословно.
Никаких вызовов модели и запуска проверяемого агента выполнять не нужно.
