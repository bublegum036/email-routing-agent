# Локальный пилот Gmail

Подготовлены приём и тестовая отправка. Реальная проверка Gmail ещё не выполнена.
Тесты используют подставные IMAP/SMTP и явно offline-модель.
Рабочая почта и реальные клиенты в этот этап не входят.

## Подготовка

1. Создай отдельный тестовый аккаунт Gmail. Включи двухэтапную проверку и создай
   пароль приложения: [инструкция Google](https://support.google.com/accounts/answer/185833?hl=ru).
   Если аккаунт не позволяет создать пароль приложения, этот способ подключения
   недоступен; не используй основной пароль. Подключение OAuth пока не реализовано.
2. В Gmail создай ярлык `email-router-pilot`. Помещай под него только письма пилота.
3. Добавь в локальный `.env` переменные `GMAIL_PILOT_ACCOUNT` и
   `GMAIL_PILOT_APP_PASSWORD`. Пароль не передавай в чат или аргументах команды.
   Для модели сохрани текущую конфигурацию Gemini Free Tier без биллинга.
4. Подготовь локальное соответствие ролей тестовым адресам:

```bash
mkdir -p artifacts/private/gmail-pilot
chmod 700 artifacts/private/gmail-pilot
cp data/gmail-pilot.example.json artifacts/private/gmail-pilot/recipients.json
```

В `allowlist` перечисли разрешённые тестовые адреса, а в `recipients` задай
соответствие роли адресу, например ключ `order_operations` для кейса mail-02.
Адреса выбирает сотрудник; они не берутся из входящего письма или ответа модели.
Пустой пример запрещает любую отправку.

Используются TLS IMAP `imap.gmail.com:993` и SMTP `smtp.gmail.com:465`:
[документация Google](https://developers.google.com/workspace/gmail/imap/imap-smtp).

## 1. Приём без отправки

Получи текст учебного письма:

```bash
.venv/bin/python -m scripts.gmail_pilot fixture-text --fixture mail-02
```

Отправь этот текст обычным текстовым письмом без подписи, HTML и вложений на
тестовый Gmail. Назначь ему ярлык `email-router-pilot`. Затем:

```bash
.venv/bin/python -m scripts.gmail_pilot fetch
.venv/bin/python -m scripts.gmail_pilot status
.venv/bin/python -m scripts.gmail_pilot fetch
.venv/bin/python -m scripts.gmail_pilot status
```

Повторное чтение того же сырого письма должно оставить одну строку inbox.
`fetched` показывает число прочитанных писем, включая уже сохранённые.
Чтение выполняется readonly с BODY.PEEK: письма не удаляются и не отмечаются
прочитанными. Максимальный размер письма 256000 байт; большие письма пропускаются.
Полное содержимое остаётся в локальной игнорируемой SQLite-базе.

Все письма получают `quarantine`. Заголовки From, Subject, Message-ID,
References и даже X-Data-Classification не подтверждают отправителя, клиента
или допустимость передачи модели. References/In-Reply-To используются только
для справочной связи с единственным известным родителем; неоднозначная связь
не устанавливается. Одинаковый Message-ID с разным содержимым сохраняет обе копии.

Скопируй SHA256 из поля `id` в status. Сотрудник явно выбирает синтетический кейс:

```bash
.venv/bin/python -m scripts.gmail_pilot process-fixture \
  --id SHA256_ИЗ_STATUS --fixture mail-02
.venv/bin/python -m scripts.gmail_pilot status
```

Это реальный вызов Gemini в режиме workflow. До вызова тело проверяется на
точное совпадение с выбранной синтетической записью. Разрешена одна часть
text/plain без вложений; неизвестное письмо остаётся в карантине. В Gemini
попадает исходный учебный кейс с учебным отправителем и учебной историей,
а не Gmail-заголовки. Это проверка транспорта и существующего учебного маршрута,
а не распознавание нового клиента или проверка его полномочий.

Каждая обработка получает отдельную папку run-UTC, чистую state.sqlite и
trace.json. Повторная обработка того же inbox id отклоняется. После сбоя статус
processing/failed и исходные файлы сохраняются; автоматического перезапуска нет.
Для нового эксперимента используй новую папку `--home artifacts/private/НОВАЯ-ПАПКА`.

В trace.json проверь получателя `order_operations` и отсутствие ошибок.
До отдельной команды send никакой SMTP-отправки не происходит.

## 2. Тестовая отправка

Из status возьми id подготовленного deliveries. Выполни:

```bash
.venv/bin/python -m scripts.gmail_pilot send \
  --id ID_ИЗ_DELIVERIES \
  --config artifacts/private/gmail-pilot/recipients.json
.venv/bin/python -m scripts.gmail_pilot status
```

Отправляется только фиксированное служебное уведомление с локальным идентификатором
`pilot:out-…`. Его можно найти через status → inbox_id → run_folder. Исходный текст,
тема входящего, клиентские данные, резюме, договоры и вложения в SMTP не попадают.
Уточнения клиенту пока остаются в локальной SQLite и не отправляются через Gmail.
Операция доступна только локальной CLI, не модели; это не разрешение выдачи
критических данных от имени сотрудника.

Проверь полученное письмо непосредственно в тестовом ящике адресата и папке спама.
Статус `accepted` означает приём SMTP-сервером, а не подтверждение доставки адресату.
Повтор send для accepted отклоняется. Исходы каждой попытки сохраняются отдельно.

При явном отказе SMTP, включая отказ аутентификации до отправки, состояние
`rejected`: после устранения причины можно
вручную повторить ту же команду. При обрыве, таймауте, аварийном завершении или
другой неопределённости остаётся `uncertain`, повтор блокируется. Сначала сотрудник
проверяет отправленные письма и ящик получателя. Автоматической гарантии exactly-once
через SMTP нет; инструмента сброса uncertain пока нет.

CLI возвращает код 0 для успешных fetch/status и завершённой process-fixture.
Неуспешная обработка возвращает 1, сохраняя failed и трассу. Для send код 0
означает accepted; rejected и uncertain возвращают 1.

Критерии реального пилота: приём без изменения Gmail-флагов; повторный fetch
без новой inbox-строки; обработка синтетического mail-02; фактическая доставка
фиксированного уведомления разрешённому тестовому адресату; блокировка повторного
send. Эти результаты ещё предстоит получить на Gmail пользователя.

## Что понадобится для рабочей почты (третий пункт)

- Рабочий ящик, его владелец и согласованный способ доступа; для организации —
  администратор Google Workspace и настройка OAuth с подходящими правами.
- Доверенные источники клиентов, договоров, заказов и заявок, правила подтверждения
  отправителя и разграничение доступа. Заголовка From для этого недостаточно.
- Классификация данных сотрудником до облачной обработки. Персональные данные,
  договоры, документооборот и неклассифицированные записи остаются у сотрудника;
  исключение для счетов не отменяет ограничения на персональные данные в них.
- Интерфейс ручного разбора: просмотр оригинала внутри доверенной среды,
  назначение ответственного, журнал действий. Критическое содержимое выдаёт
  и пересылает только сотрудник.
- Правила хранения и удаления, защищённое хранение учётных данных, резервное
  копирование, восстановление после сбоев и разбор неопределённых доставок.
- Ограниченный круг участников, критерии приёмки и способ остановить пилот.

Третий пункт отложен. Проверка Gmail первых двух пунктов не включает эти функции.
