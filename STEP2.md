# Шаг 2. Инструменты автоматического диспетчера

Основание: [задание, шаг 2](README.md) и [границы первой версии](STEP1.md).
Автор выбрал **вариант 2 интерфейсов: отдельное чтение источников и общая
операция передачи обращения**. Это отдельный выбор от варианта первой версии
в шаге 1. Ниже — проект контрактов; функций и работающего агента пока нет.

## Рассмотренные варианты

| Вариант | Как получает сведения и действует | Компромисс |
|---|---|---|
| 1. Весь контекст сразу | Один вызов собирает клиента, переписку, договор, заказ и заявки | Меньше обращений к модели, но больше ненужных сведений; выбор источников скрыт в коде |
| **2. Раздельное чтение, общая передача — выбран** | Модель выбирает источники; создание/дополнение заявки и внутренняя пересылка выполняются вместе | Нужные сведения читаются по мере необходимости, меньше отдельных действий с побочными эффектами |
| 3. Каждая операция отдельно | Отдельные инструменты создания заявки, дополнения, пересылки, уведомления | Больше шагов и состояний частичного выполнения |
| 4. Поиск ссылок, затем чтение записей | Сначала находятся идентификаторы, затем модель запрашивает документы | Полезно для больших баз, избыточно для небольшого стенда |

Для небольших учебных данных предварительный порядок расходов на модель:
1 → 2 → 3 → 4. Это предположение, а не измеренная стоимость: объём результатов,
число обращений к модели и длина истории могут поменять порядок. На большой
базе выдача всего контекста может оказаться дороже выборочного чтения.

## Как модель обращается к инструментам

Модель получает описания функций и схемы аргументов, предлагает имя функции
и параметры. Программа проверяет вызов, выполняет его и возвращает
структурированный результат модели. По результату модель выбирает следующий
шаг. Такой обмен описан в [документации по tool use](https://platform.claude.com/docs/en/agents-and-tools/tool-use/overview).
Этот источник объясняет механизм и не означает выбор провайдера для проекта.

Условная запись `get_order(customer_id, order_id)` ниже описывает параметры,
которые передаёт модель. Программа сама добавляет контекст текущего письма:
`message_id`, адрес отправителя, цепочку переписки, дату обработки, идентификатор
запуска. Модель не может подменить отправителя или выбрать чужую цепочку.
Неизвестные поля и неверные типы аргументов отклоняются.

## Общие правила результатов

Чтение возвращает объект с `status`, `data`, `candidates`, `error` и `evidence_id`.
Неиспользуемые поля имеют значения `null` или `[]`. `evidence_id` выдаётся
программой для сохранённого наблюдения, а не придумывается моделью.

| Статус | Значение | Что делать дальше |
|---|---|---|
| `found` | Найдена одна запись или достоверно определённый набор сведений | Использовать факты и их источник |
| `not_found` | Поиск выполнен, подходящих записей нет | Уточнить сведения; для поиска открытых заявок допустимо создание новой |
| `ambiguous` | Есть несколько возможных совпадений или связь с вопросом не установлена | Прочитать дополнительный источник, уточнить или передать сотруднику |
| `unverified` | Компания может быть найдена, но связь отправителя с ней не подтверждена | Не выдавать сведения компании; уточнить или передать сотруднику |
| `forbidden` | Запись вне разрешённого отправителю контекста | Не раскрывать содержимое, передать на ручную проверку |
| `unavailable` | Источник временно недоступен; результат поиска неизвестен | Не считать запись отсутствующей; ограниченный повтор или ручная передача |
| `invalid_arguments` | Неправильный формат или несовместимые параметры | Исправить аргументы без повторения того же вызова |

`unverified` используется при определении клиента. Точное чтение заказа не
возвращает `ambiguous`: уникальный номер даёт одну запись либо другой статус.
Набор применимых статусов уточнён у каждой функции. Ошибка содержит `code`
и короткое описание без содержимого чужих записей. `forbidden` не сообщает
название чужого клиента или детали его заказа.

Дата фактов и версия записи сохраняются вместе с наблюдением. Состояния оплаты,
отгрузки и обслуживания могут быть `unknown`: найденная запись с неизвестным
полем не разрешает угадывать значение.

## Пять инструментов чтения

### 1. `resolve_customer(company_hint?, reference_id?)`

**Описание для модели:** «Определи клиента текущего письма по зарегистрированным
контактам. Если есть несколько вариантов, используй известное название или
номер договора, заказа, заявки из письма/прочитанной истории. Совпадение имени
не подтверждает принадлежность отправителя к компании».

- **Аргументы:** оба необязательны. `company_hint` — название из письма;
  `reference_id` — точный D-/O-/T-номер из письма или уже прочитанной истории.
  Без аргументов проверяются зарегистрированные связи отправителя.
- **Результат:** `customer_id`, название, `identity_status: verified`, основание
  подтверждения и `sales_owner_ref`; при неоднозначности — минимальный список
  допустимых кандидатов без договоров и заказов.
- **Особые ответы:** нет совпадений — `not_found`; несколько — `ambiguous`;
  найденная по названию компания без подтверждённого контакта — `unverified`;
  реестр недоступен — `unavailable`.
- **Ограничение:** reference_id помогает выбрать компанию только среди
  подтверждённых связей отправителя. Знание номера договора не является
  доказательством полномочий. Для незнакомого отправителя достаточно запросить
  реквизиты для ручной проверки; само сообщение с реквизитами его не авторизует.
- **Риск ошибки:** выбор чужого клиента и последующая утечка. Проверку связи
  выполняет код по локальному реестру, а не модель по похожести имени.
- **Нужен для:** писем 1–7.

### 2. `read_thread()`

**Описание для модели:** «Прочитай предыдущие сообщения только в цепочке
текущего письма, чтобы найти обсуждавшиеся номера и варианты. Не ищет по всей
почте и не подтверждает истинность утверждений участников».

- **Аргументы:** нет; идентификатор цепочки программа берёт из входящего события.
- **Результат:** список `{message_id, sent_at, sender, text}`, связанные номера
  и `complete: true`. Полный текст договоров и посторонние цепочки не включаются.
- **Особые ответы:** нет истории — `not_found`; нельзя однозначно установить
  цепочку — `ambiguous`; хранилище недоступно — `unavailable`. Неполная история
  помечается `complete: false` и не считается доказательством отсутствия контекста.
- **Риск ошибки:** неверная связь письма с чужой перепиской. Связь задаёт локальная
  почтовая система, не адрес или номер цепочки, предложенный моделью.
- **Нужен для:** писем 1, 5; при необходимости для 4 и 7.

### 3. `get_contract(customer_id, contract_id?)`

**Описание для модели:** «Получить срок и уровень обслуживания, назначенную
группу и ответственного за договор подтверждённого клиента. Не выдаёт полный
текст договора. При нескольких подходящих договорах не выбирает первый».

- **Аргументы:** `customer_id` — из успешного `resolve_customer`;
  `contract_id` — из письма/истории. Если номер неизвестен, ищутся договоры
  клиента; несколько договоров без способа выбрать нужный дают `ambiguous`.
- **Результат:** `{contract_id, customer_id, service_status, valid_from,
  valid_until, service_level, support_group_ref, contract_owner_ref}`.
  `service_status`: `active | expired | unknown` на дату обработки;
  `service_level`: `standard | extended | unknown`.
- **Особые ответы:** нет договора — `not_found`; несколько — `ambiguous`;
  чужой договор — `forbidden`; источник недоступен — `unavailable`.
- **Риск ошибки:** неправильная группа или обещание недоступного обслуживания.
  Для маршрутизации требуются определённое состояние и соответствующий адресат.
- **Нужен для:** писем 1 и 6.

### 4. `get_order(customer_id, order_id)`

**Описание для модели:** «Получить подтверждённые состояния оплаты и отгрузки
одного заказа клиента по точному номеру. Не изменяет заказ и не вычисляет
обещанную дату доставки из текста письма».

- **Аргументы:** `customer_id` — из `resolve_customer`; `order_id` — из письма
  или прочитанной истории, например `O-52`.
- **Результат:** `{order_id, customer_id, payment_status, shipping_status,
  tracking_number, confirmed_delivery_date}`. Два последних поля могут быть
  `null`. Оплата: `paid | unpaid | pending | unknown`; отгрузка:
  `not_shipped | shipped | delivered | unknown`.
- **Особые ответы:** номера нет — `not_found`; заказ другого клиента —
  `forbidden`; источник не ответил — `unavailable`. Несколько результатов
  для одного уникального номера — ошибка целостности `unavailable`, не выбор модели.
- **Риск ошибки:** неверный исполнитель или выдуманные факты. Слова «оплатили»
  и «груз» в письме не заменяют состояния из источника.
- **Нужен для:** писем 2, 3 и 7.

### 5. `find_tickets(customer_id, subject, ticket_id?, order_id?)`

**Описание для модели:** «Найти существующие обращения клиента по этому вопросу
до создания нового. При известном T-номере проверь конкретную заявку,
включая статус и текущего исполнителя. Несколько похожих заявок не объединяй».

- **Аргументы:** `customer_id` — из разрешённого определения клиента;
  `subject` — короткое описание вопроса из письма и истории; `ticket_id` и
  `order_id` — только известные номера. `subject` обязателен и при T-номере:
  нужно проверить, что речь идёт о той же проблеме.
  Для вопроса о конкретном заказе `order_id` обязателен даже при наличии
  номера в `subject`; это проверяется до поиска.
- **Результат:** `{ticket_id, customer_id, status, assignee_ref, subject,
  order_id, thread_link, match_basis}` для найденного обращения.
  `match_basis` показывает основания связи: например, точный номер и совпадающая
  тема либо уже сохранённая связь цепочки с заявкой. Одного совпадения заказа
  недостаточно для признания двух проблем одним обращением.
- **Особые ответы:** нет связанного обращения — `not_found`; несколько
  кандидатов или недостаточно данных для установления связи — `ambiguous`;
  чужая заявка — `forbidden`; источник недоступен — `unavailable`.
  Закрытая заявка по точному номеру — `found` со статусом `closed`, затем человек.
- **Риск ошибки:** дубль при пропущенной заявке или присоединение другого вопроса.
  Поиск по тексту не гарантирует идеального совпадения; сомнительная связь
  требует ручного решения, а не автоматического объединения.
- **Нужен для:** писем 1–7 перед передачей определённого вопроса.

## Три инструмента действий

Для каждого выделенного вопроса программа назначает стабильный `issue_id`.
Для письма 7 их два. Модель использует выданные идентификаторы; при повторе
события программа восстанавливает прежние вопросы. Детали выделения вопросов
и их сохранения будут определены в архитектуре на шаге 3.

Общие параметры действий: `issue_id` и `evidence_ids` — ссылки на наблюдения
текущего контекста. Ссылка не заменяет проверку: код сверяет факты с источником.
Адрес получателя не принимается как произвольная строка из письма.
У всех трёх действий возможны `invalid_arguments`, `unavailable`, `conflict`
и `already_applied`. `unavailable` до записи означает отсутствие изменений;
при потере ответа результат восстанавливается повтором с прежним ключом,
а не считается заведомо невыполненным. Специальные случаи указаны ниже.

### 6. `route_request(issue_id, customer_id, category, target_ref, summary, evidence_ids, ticket_id?)`

**Описание для модели:** «Передать один определённый вопрос разрешённому
внутреннему исполнителю: создать новую рабочую заявку или дополнить указанную
открытую, сохранив внутреннюю пересылку исходного письма. Не оформляет
коммерческий заказ, не продлевает договор и не запускает работы».

- **Аргументы:** `customer_id` — из определения клиента; `category`:
  `technical | order | purchase | approval`; `target_ref` — идентификатор роли
  `order_operations`, `logistics`, `general_support` либо назначенной группы/
  сотрудника из результатов чтения; `summary` — краткий вопрос и факты для
  исполнителя. `ticket_id` берётся из `find_tickets`; отсутствие означает запрос
  создания новой заявки, а не разрешение пропустить проверку существующих.
- **Проверки:** подтверждён клиент; источники доступны; поиск по этому вопросу
  выполнен; данные относятся к клиенту; исполнитель соответствует фактам.
  Открытая связанная заявка имеет приоритет маршрутизации к текущему исполнителю.
  Для новой технической заявки нужен договор; для новой заявки о заказе — заказ;
  для покупки/согласия — разрешённый ответственный за продажи и контекст.
  Отсутствующий ответственный не заменяется выдуманным адресом.
- **Результат:** `status: applied`, `action_id`, `ticket_id`, `ticket_operation:
  created | appended`, `recipient_ref`, фактический тестовый `recipient_address`
  и `outgoing_message_id`. Все поля ссылаются на сохранённые записи стенда.
- **Особые ответы:** указана ненайденная заявка — `not_found`; несколько
  возможных заявок/маршрутов — `ambiguous`; не хватает проверок или нарушено
  правило — `blocked` с кодом причины; недоступно хранилище — `unavailable`.
  При несуществующей указанной заявке автоматического создания взамен нет.
- **Риск ошибки:** ложная пересылка, неверная заявка, дубль. Код повторно
  проверяет статус/исполнителя и состояние источников непосредственно перед
  записью; изменившиеся факты дают `conflict` и требуют перечитать их.
- **Нужен для:** определённых вопросов писем 1–7.

### 7. `request_clarification(issue_id, missing_fields, evidence_ids)`

**Описание для модели:** «Запросить у отправителя конкретные недостающие
сведения без раскрытия найденных у других клиентов данных. Не ждёт ответа
внутри текущего запуска».

- **Аргументы:** `missing_fields` — непустой список из `company_identifier`,
  `order_id`, `ticket_id`, `proposal_reference`, `equipment_details`,
  `problem_details`. Выбирается по отсутствующим сведениям. Для случая, который
  не покрывается этими вопросами, используется ручная передача.
- **Выполнение:** текст формируется из шаблонов вопросов. Получатель —
  нормализованный адрес отправителя из входящего события, без адресов из тела
  письма или произвольного `Reply-To`. Клиентские документы не прикладываются.
  Для `company_identifier` сначала нужна попытка определения клиента.
  При неоднозначном клиенте и доступной истории нельзя запрашивать реквизиты,
  пока история не прочитана; для незнакомого отправителя это требование не действует.
- **Результат:** `status: applied`, `action_id`, `outgoing_message_id`,
  `recipient_address`, `missing_fields`. Отдельно фиксируется итог вопроса:
  `awaiting_customer`; это не решённая техническая проблема.
- **Особые ответы:** недопустимое/пустое поле — `invalid_arguments`; нет
  допустимого обратного адреса — `blocked` и ручная передача; неизвестен результат
  записи — восстановление результата по стабильному ключу. Отсутствие клиента
  допустимо; `ambiguous` здесь неприменим, клиент по этому вызову не выбирается.
- **Риск ошибки:** ненужное уточнение, повторные письма, утечка через формулировку.
  Шаблоны не перечисляют чужие договоры и варианты найденных компаний.
- **Нужен для:** писем 5, 6 и альтернатив с недостаточными сведениями в 1–4, 7.

### 8. `handoff_to_human(issue_id, reason, summary, evidence_ids)`

**Описание для модели:** «Сохранить вопрос для ручного разбора с причиной,
уже известным контекстом и недостающими проверками. Не считать ручную передачу
подтверждением выполнения запрошенной клиентом операции».

- **Аргументы:** `reason`: `identity_unverified | ambiguous_context |
  source_unavailable | closed_ticket | forbidden_request | conflicting_facts |
  missing_owner | unsupported_case`. `summary` объясняет, что должен решить
  сотрудник. При запрете из письма 8 `evidence_ids` может быть пустым:
  исходное письмо программа связывает автоматически, договор читать не нужно.
- **Результат:** `status: applied`, `action_id`, `review_id`, `queue_ref`,
  `reason`. Очередь выбирает код по конфигурации стенда: обычно `human_review`,
  для подтверждённого неотгруженного заказа с неподтверждённой оплатой —
  `order_operations` для ручной сверки. Модель не передаёт произвольную очередь.
- **Особые ответы:** исходное событие не найдено — `not_found`; неправильная
  причина — `invalid_arguments`; хранилище недоступно — `unavailable`.
  `ambiguous` не применяется: получатель ручной передачи задан заранее.
- **Риск ошибки:** неоправданная передача человеку вместо доступного решения
  или потеря вопроса. Проверяем сохранённую запись и причину по ожиданиям сценария.
- **Нужен для:** письма 8 и неопределённых/ошибочных веток остальных писем.

### Сохранение и повторы действий

Для локального стенда создание/дополнение заявки и запись исходящей пересылки
проектируются одной транзакцией в локальном хранилище. Исходящее сообщение
стенда — и есть проверяемая отправка; реальная SMTP-доставка в этот контракт
не входит. Поэтому нельзя получить половину успешной локальной передачи.

Программа вычисляет ключ повтора из исходного письма, стабильного вопроса
и операции. Повтор того же запроса возвращает `already_applied` с прежними
идентификаторами. Изменение параметров при том же ключе даёт `conflict`.
После потерянного ответа повтор с тем же ключом восстанавливает результат.
Переименование вопроса моделью не должно позволять повторить действие:
идентификаторы и связь с событием сохраняет программа. После итоговой передачи
второе несовместимое действие по тому же вопросу блокируется. Если не удалось
сохранить даже ручную передачу, запуск считается ошибочным, а не завершённым.

из таблицы задания без изменения их бизнес-фактов. Для работы инструментов
добавим только явно заданные тестовые контакты и внутренние адреса, роли

## Как инструменты покрывают восемь писем

Последовательности иллюстративны: допустимы другие порядки чтения с тем же
результатом. `find_tickets` выполняется перед передачей каждого определённого
вопроса; если он находит связанную открытую заявку, используется её исполнитель.

| № | Источники и следующие шаги | Ожидаемый результат на предложенных данных |
|---|---|---|
| 1 | `resolve_customer` → неоднозначность; `read_thread` → D-12; `resolve_customer(reference_id="D-12")` → C-12; `get_contract` → обслуживание закончено; `find_tickets` | При отсутствии прежней заявки `route_request` ответственному за D-12, Марине |
| 2 | `resolve_customer` → C-21; `get_order` → O-52 оплачен, не отгружен; `find_tickets` | При отсутствии прежней заявки `route_request` в обработку заказов |
| 3 | `resolve_customer(reference_id="O-51")` → C-11; `get_order` → отгружен; `find_tickets` | При отсутствии прежней заявки `route_request` в логистику |
| 4 | `resolve_customer` → C-31; `find_tickets(ticket_id="T-9", subject=...)` → открыта, Сергей | `route_request(ticket_id="T-9")`: дополнение и уведомление Сергея без новой заявки |
| 5 | `read_thread` → предложение для C-11 («Вектор Север»), второй вариант — пять комплектов; `resolve_customer(company_hint="Вектор Север")` → C-11 при подтверждённой связи; `find_tickets` | Передача согласия ответственному за продажи, без оформления заказа/списания денег |
| 6 | `resolve_customer(company_hint="Вектор")` → связь не подтверждена | `request_clarification` с реквизитами компании и деталями проблемы либо обоснованная ручная передача |
| 7 | `resolve_customer` → C-21; два вопроса; `get_order` для O-52; отдельный `find_tickets` для каждого вопроса | Пять комплектов — продажам; задержка O-52 — обработке заказов; два сохранённых результата |

## Проверка одного интерфейса на бумаге

Проверяем описание `get_order` на письме 2, без кода агента.

1. Из письма человек может взять `order_id="O-52"`.
2. Имени Олег недостаточно для `customer_id`. По описанию нужно сначала вызвать
   `resolve_customer()`, который при зарегистрированном контакте вернёт C-21.
3. После этого параметры однозначны:

```json
{"customer_id":"C-21","order_id":"O-52"}
```

Пример ответа (идентификатор наблюдения условный):

```json
{
  "status": "found",
  "data": {
    "order_id": "O-52",
    "customer_id": "C-21",
    "payment_status": "paid",
    "shipping_status": "not_shipped",
    "tracking_number": null,
    "confirmed_delivery_date": null
  },
  "candidates": [],
  "error": null,
  "evidence_id": "obs-order-01"
}
```

Три варианта ответа и решения:

| Вариант | Ответ | Как его понять |
|---|---|---|
| А | `found`, `paid`, `not_shipped` | Новый вопрос после проверки заявок передать обработке заказов; срок неизвестен |
| Б | `not_found`, `data: null` | Уточнить номер; оплата и отгрузка неизвестны |
| В | `unavailable`, `data: null`, `error.code: "source_timeout"` | Источник не ответил; нельзя утверждать, что заказа нет; ограниченный повтор либо ручная передача |

Исправление интерфейса при разборе: вместо свободного запроса «проверь заказ
Олега» нужны точные `customer_id` и `order_id`. При этом не требуем от модели
адрес отправителя: его надёжнее подставлять программой. Это самостоятельная
проверка описания, не испытание с независимым участником и не запуск программы.

## Большой инструмент против разделённых на письме 2

| Подход | Чтения до выбора действия | Лишние данные | Проверка |
|---|---|---|---|
| Весь контекст | Один вызов, внутри которого код читает источники | Может вернуть договор и историю, не нужные для O-52 | Нужны отдельные статусы источников, иначе непонятно, где был сбой |
| Выбранный вариант | Три: клиент, заказ, поиск заявки | Только данные клиента, O-52 и связанные обращения | Можно отдельно проверить принадлежность, оплату, отгрузку и прежнюю заявку |
| Поиск ссылок с чтением | Поиск клиента/записей и дополнительные чтения результатов | Мало содержимого до выбора записей | Хорошо для больших источников, но больше промежуточных шагов |

Число вызовов инструмента не равно числу вызовов модели: некоторые независимые
вызовы можно выполнить вместе. Для данного письма заказ и поиск заявки зависят
от уже найденного клиента. Стоимость пока не измерена.

## Что исключено

- Интернет-поиск: состояния локальных договоров и заказов не проверяются
  публичным поиском. Интернет использовался при проектировании, но не входит
  в инструменты почтового агента.
- Изменение тарифа, оплаты, договора или коммерческого заказа: за пределами
  выбранной самостоятельности; новая потребность передаётся продажам.
- Удаление писем: для маршрутизации не нужно, исходное письмо требуется
  для проверки результата.
- Произвольная отправка с адресом и вложением от модели: заменена ограниченными
  передачей ответственному и запросом уточнения отправителю.

Каждый выбранный инструмент связан со сценарием, источники параметров описаны,
отсутствие записи отделено от сбоя. На шаге 3 предстоит определить цикл агента,
контроль выполнения, лимиты и хранение состояния. Провайдер и модель пока
не выбраны; рабочий код появляется на шаге 4.
