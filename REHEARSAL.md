## Подготовить перед показом

Открыть DEFENSE.md, STEP2.md, STEP3.md, STEP8.md, STEP9.md и панель
http://localhost:13000/d/email-router-local. Проверить стенд:

```sh
.venv/bin/python monitoring/manage.py check
```

Для повторяемой демонстрации текущего кода без API:

```sh
.venv/bin/python -m scripts.rehearse
```

Команда проверяет mail-09, mail-02, order-shipped, critical-boundary и
order-missing-shipping в обоих режимах, каждый раз с отдельной базой.
Новая папка создаётся в artifacts/private/defense-rehearsal-<UTC>.
Ожидания фиксируются до обработки; результаты, JSON/JSONL и SQLite сохраняются.
Используются явные сценарные ответы RegressionFixture. Это демонстрация
контроллера и проверок; она не подтверждает качество выбора инструментов Gemini.
Существующая папка не переиспользуется. Критическая граница не вызывает модель.

## Короткие ответы на вопросы

1. **Зачем выбор следующего шага моделью?** Для неодинакового пути поиска
   контекста и нескольких вопросов. На наших исторических независимых письмах
   преимущества по конечному результату не обнаружено.
2. **Почему route_request составной?** Проверки и запись заявки/служебного
   уведомления выполняются вместе; модель не должна вручную собирать
   небезопасную последовательность записей.
3. **Когда фактов достаточно?** Подтверждены клиент, данные выбранной ветки,
   поиск заявки по вопросу и реально полученные evidence_ids; код перепроверяет.
4. **Что не доверяем модели?** Полномочия внешнего получателя, выдачу договоров,
   персональных данных и разрешение отправки за сотрудника.
5. **Что показала ошибка?** Доступность источника не означает полноту записи.
   Структурно неполный ответ нельзя лечить повтором и подстановкой текста письма.
6. **Может ли workflow быть выгоднее?** В первоначальном независимом наборе
   оба режима прошли 4/4, workflow — 4 вызова против 20. Новую оценку стабильности
   agent надо анализировать отдельно; время включает паузы, деньги не измерялись.
7. **Что ещё ограничено?** После регистрации вопросов и частичного исполнения
   модель не умеет безопасно добавить пропущенный вопрос в разбиение. Требуется
   сотрудник. Для произвольной почты полнота поиска и извлечения не доказана.

## Новый полный agent и сравнение режимов

```sh
.venv/bin/python -m email_router.regression --mode agent
```

17 кейсов × 3 попытки, каждый с чистой базой. Критический кейс должен пройти
без API; остальные могут потребовать несколько запросов модели. Не меняй
Python-модули email_router, seed и ожидания во время прогона и его продолжений.
Скрипты репетиции и сравнения находятся вне email_router и не меняют
зафиксированный runtime существующего workflow.

При ошибке API сохранить вывод и продолжить после восстановления доступа/квоты:

```sh
.venv/bin/python -m email_router.regression --mode agent \
  --continue-from artifacts/ПАПКА-ПРЕДЫДУЩЕГО-ПРОГОНА
```

Продолжение выполняет только незапущенные слоты и сохраняет ошибку в первом
слоте. Для сравнения нужна последняя папка продолжения с pending=0.
Полный итог может быть меньше 51/51 — это результат эксперимента.

После завершения:


Проверяются одинаковые данные, ожидания, код и параметры, единственная одинаковая
фактическая модель во всех ответах обоих прогонов,
полные три слота и уникальность попыток. Ошибки и неизвестные расходы остаются
видимыми. Одинаковый API-алиас не доказывает неизменность весов провайдера.
Прежняя команда regression --compare сравнивает версии одного режима;
для разных режимов используется scripts.compare_modes.

Прогон завершён без API-ошибок и незапущенных слотов. Выполненная команда

### Спорные повторы и ограничения метрик

У agent 15 отклонений: 10 invalid_arguments из-за ненаблюдавшегося company_hint,
три преждевременных уточнения до чтения истории, один маршрут без поиска заявки
и один маршрут без подтверждённого заказа. Ни одно не является выполненной
запрещённой пересылкой. Сохранённые эффекты проверены отдельно.

Счётчик planned_technical_retries показывает 6 у workflow и 8 у agent, но его
название шире фактического планового повтора: он считает любое повторение
одинакового чтения после unavailable в сценариях сбоев. Разбор первой
agent-попытки order-unavailable показывает четыре unavailable вместо
необходимой пары. После исчерпанного первого повтора модель ещё раз запросила
тот же заказ, а контроллер повторил это чтение. Поэтому фактически в обоих
режимах шесть предусмотренных повторов; у agent ещё два дополнительных
без новых данных. Исходные метрики не переписаны ради более удобного названия.
У workflow три repeated_argument_calls — повторное чтение истории mail-05;
это отдельный кандидат на сокращение. У agent этот счётчик равен нулю, потому
что дополнительные unavailable-чтения отнесены к planned_technical_retries.
