# Шаг 8. Регрессионный набор и сравнение версий

Выбран программный проверяющий код с повторными запусками Gemini. Рассмотрены
три варианта: только локальные тесты; тесты и реальные прогоны; дополнительно
LLM-оценщик. Для маршрутов, сохранённых эффектов и запретов достаточно второго.
Качество свободного пояснения отдельно не оценивается: оно не отправляется
автоматически вместе с клиентскими данными.

## Зафиксированный набор

`data/evaluation-regression-v1.json`: 17 кейсов. Первые восемь перенесены из
набора разработки, ещё четыре — из прежнего независимого набора. Их ожидания
сохранены дословно. Эти четыре письма теперь известны и считаются регрессионными;
старые файлы и первоначальная независимая оценка не изменены.

Добавлены пять вариантов существующих источников и писем:

| Кейс | Изменение | Ожидание |
|---|---|---|
| order-transient | Первый get_order недоступен | Технический повтор, затем order_operations |
| order-unavailable | Все чтения заказа недоступны | Повтор и source_unavailable, без письма и новой заявки |
| order-shipped | Только O-52.shipping_status = shipped | logistics после подтверждения источником |
| order-missing-shipping | Удалено только O-52.shipping_status | Наблюдение неполной записи, управляемый ручной разбор |
| critical-boundary | Синтетический D-12 классифицирован critical | Ноль вызовов модели, ручной разбор, редактированный экспорт |

Новые клиентские факты не добавлены. Объединённый исходный стенд — существующий
`data/seed-held-out.json`. Проверяется рекурсивная синтетическая классификация
до создания файлов и открытия Store. Критическая классификация в последнем
кейсе ставится только после загрузки проверенных имитационных записей; это
проверка облачной границы, а не разрешение подавать реальные договоры на вход.

До первого обращения сохраняются expectations.json, seed.json, версии модулей
и конфигурация. Модель получает письмо и доступные источники, без эталонов.
Объявленные routes/outcome применяются ко всем вариантам; специальные проверки
восстановления, наблюдения источника и критической границы добавляются к ним.
Несовместимые с вариантом ожидания отклоняются до создания файлов и запуска
обработчика, в том числе при прямом вызове attempt().
Каждый повтор имеет отдельную SQLite и уникальный run_id. В JSONL case_id
обозначает регрессионный вариант; runtime_case_id сохраняет исходный ID из
обработчика. Исходный JSON обработчика не переписывается ради этих обозначений.

## Одна команда после изменения

Полная локальная проверка, включая отрицательные тесты найденных дефектов:

```sh
.venv/bin/python -m email_router.regression --offline --with-unit-tests
```

Она выполняет unittest, затем 17 × 3 × 2 = 102 попытки с явной подстановкой.
Это проверка инфраструктуры и бизнес-правил, не измерение качества Gemini.
Найдённые дефекты экспорта, порядка доказательств, повторного использования базы,
снимка входа и завершения ошибочного вызова покрывают соответствующие unittest.
Нельзя надёжно воспроизвести ошибку парсинга провайдера обычным успешным ответом
Gemini; для неё используется отрицательный локальный тест.

Реальный набор в одном режиме — 51 попытка, в обоих — 102. Вызовов API будет
больше числа попыток, особенно в agent. Платный fallback не добавлен.

```sh
.venv/bin/python -m email_router.regression --mode workflow
```

Для agent заменить workflow на agent; для обоих указать both или опустить
--mode. Результаты находятся в новой папке artifacts/live-regression-…:
summary.json, results.md, ожидания, исходный стенд, снимок модулей code/ и папки отдельных попыток
с seed.json, state.sqlite, trace.json и trace.jsonl. Исходящие существуют
только в учебной SQLite; успешная квитанция не означает реальную SMTP-доставку.

При ошибке модели дальнейшие запросы прекращаются. Ошибка остаётся неуспехом;
оставшиеся слоты отмечены как незапущенные. Продолжение, например:

```sh
.venv/bin/python -m email_router.regression --mode workflow \
  --continue-from artifacts/live-regression-ПАПКА-ПРЕДЫДУЩЕГО-ЗАПУСКА
```

Продолжение требует неизменных кода, стенда, ожиданий, режима и конфигурации.
Оно создаёт новую папку, сохраняет ссылки на все прежние попытки и выполняет
только незапущенные слоты. Неуспешный первый повтор не заменяется успешным
четвёртым. Код выхода остаётся 1, если сохранилась хотя бы одна ошибка.
Начало попытки журналируется до исполнения: даже прерывание процесса остаётся
в знаменателе. Для прерванного слота без JSONL доступны папка и SQLite первой
попытки; неизвестное число вызовов не выдаётся за нулевое.

## Старый и новый обработчик

Выбранное на шаге 7 исправление — валидация обязательных полей заказа и отказ
от повторения структурно неполного ответа как временного сетевого сбоя.
До: c4f8f07; после самого исправления: 8884b7c. Сравнивается комплект runtime:
runner, tools, schemas, store, policy, llm и demo_model. Проверяющая программа,
ожидания и данные остаются текущими и одинаковыми для обеих версий.

--runtime-ref извлекает эти модули из локального Git во временную папку,
не переключая рабочую ветку. Полный commit ID и хеши модулей записываются
в отчёт. Остальные модули — текущая измерительная инфраструктура; это
контролируемое сравнение runtime, а не заявление о запуске всего старого дерева.
Секреты в копию не записываются. Конфигурация передаётся процессу через среду.

Реальное сравнение Gemini в выбранном режиме:

```sh
.venv/bin/python -m email_router.regression --mode workflow \
  --runtime-ref c4f8f07 --directory artifacts/step8-gemini-before

.venv/bin/python -m email_router.regression --mode workflow \
  --runtime-ref 8884b7c --directory artifacts/step8-gemini-after

.venv/bin/python -m email_router.regression \
  --compare artifacts/step8-gemini-before artifacts/step8-gemini-after \
  --output artifacts/step8-gemini-comparison.md
```

Нужны новые имена папок и файла, если они уже существуют. Первая команда может
завершиться с кодом 1 из-за ожидаемого дефекта: её не нужно удалять или считать
не состоявшимся экспериментом. Для продолжения старой версии необходимо снова
передать тот же --runtime-ref вместе с --continue-from и новым --directory.
Для полной оценки обоих режимов заменить workflow на both в обеих командах.
API-алиас модели может обновиться у провайдера: одинаковый ID не доказывает
неизменность весов. Сравнение наблюдательное; его нельзя объяснять только кодом
при изменении фактической модели или условий API.

## Метрики и границы проверки

Успех / все запущенные попытки включает ошибки API и прерывания. pass@3 и
pass^3 считаются по 17 кейсам отдельно для каждого режима, только после трёх
попыток каждого кейса. До этого итоговые доли null. Успешный исход хотя бы
одного повтора и успех всех трёх показываются отдельно.

Считаются маршруты, неверные получатели и лишние маршруты, недостающие
автоматические действия, ручные передачи и допустимые причины, блокировки,
invalid_arguments, остановки бюджета, вызовы, известные токены и среднее время.
Отсутствующий usage отмечается отдельно; известная сумма токенов не включает
неизвестные расходы. Время включает API и установленную паузу между запросами,
ожидание сотрудника не измеряется. Денежная стоимость не оценивается.

Фактическое содержимое служебного уведомления сравнивается с фиксированным
шаблоном. Уточнение сверяется с независимым фиксированным набором вопросов
по missing_fields связанной квитанции: проверяются текст, исходный отправитель,
ссылки на письмо/вопрос и отсутствие вложений. Неизвестные, пустые или повторные
поля, произвольный текст и дополнительные поля считаются нарушением.
forbidden_content_effects влияет на итоговый passed, а не только на диагностику. Проверки
результата также проверяют запрет лишних писем/заявок, сохранение исполнителя,
источников и критической облачной границы. blocked_attempts показываются
отдельно от выполненных эффектов. Доля ложных маршрутов при отсутствии
маршрутов и доля оправданных ручных передач при отсутствии передач равны null.

repeated_argument_calls — сигнал повторения одинаковых имени и аргументов,
а не автоматический вердикт о бесполезном вызове. Плановый повтор после
unavailable в двух сценариях сбоев вынесен отдельно. В offline-трассах:
workflow повторно читает историю mail-05; agent повторяет resolve_customer
для второго вопроса mail-07. Второй случай нужен для отдельного вопроса;
первый — кандидат на устранение избыточного чтения. Их нельзя складывать
с техническими повторами и называть все вызовы ошибками.

## Выполненное сравнение workflow с повторным использованием успешного прогона

Сравниваем runtime c4f8f07 и текущий комплект обработчика, сохранённый в
artifacts/live-regression-20261019T203453740389Z/code/. У последнего уже есть
51/51 реальных попыток. Проверено совпадение всех хешей модулей с текущими
файлами проверяющей программы; BUSINESS и EXTRACT совпадают со старой версией.
Текущий runtime включает исправление обязательных полей источника и изменения
трассировки. Это сравнение двух комплектов runtime; изолированное сравнение
самого исправления c4f8f07 → 8884b7c сохранено отдельно как offline.

Для выбранного workflow использован прежний успешный прогон нового комплекта.
Старый комплект выполнен на том же наборе; команды выполненного сравнения:

```sh
.venv/bin/python -m email_router.regression --mode workflow \
  --runtime-ref c4f8f07 --directory artifacts/step8-workflow-before-final
```

После завершения всех 51 попыток построена таблица:

```sh
.venv/bin/python -m email_router.regression \
  --compare artifacts/step8-workflow-before-final artifacts/live-regression-20261019T203453740389Z \
  --output artifacts/step8-workflow-live-comparison.md
```

Известный дефект старой версии может дать код выхода 1; это сохранённый результат,
а не основание удалять попытки. При ошибке API сначала нужно закончить
незапущенные слоты через --continue-from с тем же --runtime-ref; тогда в
--compare передаётся последняя папка продолжения. После изменения Python-модулей
проверяющей программы повторное использование текущего успешного прогона может
быть отклонено: необходимо одинаковое измерение обеих версий.

В среде инструмента Codex на момент подготовки команды DNS
для generativelanguage.googleapis.com недоступен. Проверка доступности не
вызывала API, не расходовала квоту и не создавала попытку обработки письма.
Оба реальных прогона выполнены пользователем в его терминале.
