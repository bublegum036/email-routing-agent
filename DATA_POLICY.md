# Передача критических данных

Правило автора проекта: не придумывать сведения; критические данные передаёт
только сотрудник. Этот документ уточняет границы ранее выбранного диспетчера
и имеет приоритет над прежними описаниями автоматической пересылки содержимого.

## Критические категории

1. Персональные данные.
2. Договоры с клиентами.
3. Документооборот, **за исключением счетов на оплату**.

Исключение для счёта относится к виду документа. Если счёт содержит
персональные данные, такие данные остаются критическими. Неизвестная
классификация требует сотрудника, а не предположения модели.
Новые операции формирования/отправки счетов в этой версии не добавлены.

## Что делает автоматическая маршрутизация

`route_request` проверяет клиентский контекст и исполнителя, создаёт либо
дополняет локальную заявку и сохраняет **служебное уведомление сотруднику**.
Уведомление содержит внутренние идентификаторы письма, вопроса и заявки,
фиксированный текст и разрешённого исполнителя. Оно не содержит исходного
письма, свободного резюме модели, договоров, вложений или значений клиентских
фактов. Любое резюме модели — предложение для проверки, не подтверждённый факт.

Одновременно создаётся запись `critical_data_review` со статусом
`awaiting_staff`, назначенная тому же сотруднику/группе. В квитанции есть
`content_delivery=requires_staff` и ссылка на проверку. Состояние `routed`
означает назначение обращения; оно не означает выдачу его содержимого клиенту.

Сотрудник открывает оригинал и источники в локальном стенде, проверяет данные
и сам решает вопрос их передачи. Автоматической отправки содержимого после
очередного ответа модели нет. Инструмент разрешения выдачи от имени сотрудника
модели не предоставляется. Интерфейс ручной отправки в текущем стенде не реализован.

`request_clarification` может отправить только заранее заданные вопросы,
без значений из источников и без вложений. `handoff_to_human` сохраняет вопрос
для сотрудника локально. При недоступном источнике система не заменяет
неизвестное значение придуманным состоянием, адресом или сроком.

## Граница облачной модели

Перед вызовом Gemini/OpenRouter программа проверяет доверенные метаданные
источников. Ни текст письма, ни модель не могут назначить себе разрешение.

- `synthetic`: явно имитационные данные учебного стенда из задания; разрешены
  для учебных вызовов. В `seed.json` добавлена только метка происхождения,
  новые клиентские факты этим изменением не создавались.
- `operational`: сотрудник явно классифицировал запись как некритическую;
  дополнительно требуется `contains_personal_data=false`. Документы при этом
  разрешаются только с `document_type=payment_invoice`; обычная операционная
  запись без документа может иметь пустой `document_type`.
- Реальные записи источника договоров всегда требуют сотрудника. Любая
  другая или отсутствующая классификация тоже считается ограниченной.

Пока применяется консервативная проверка всего набора источников: наличие
критической/неизвестной записи останавливает облачную обработку до разбора
сотрудником. Это может остановить и несвязанный запрос. Выборочная очистка
контекста до безопасных полей ещё не реализована. Автоматического распознавания
всех персональных данных в произвольном тексте нет: классификация — доверенные
метаданные источника, устанавливаемые сотрудником.

Полные критические данные остаются в локальном хранилище для сотрудника.
Обычный JSON-отчёт для такого запуска содержит только ссылки и состояния:
текст письма, адрес отправителя и свободное содержимое событий скрываются.
SQLite-базы исключены из Git. Существующие исторические трассы содержат только
прежние учебные имитационные сведения; они не переписываются задним числом.

## Проверки

Проверяются отсутствие исходного текста/резюме/вложений в уведомлении,
создание обязательного ручного разбора, запрет подставить `staff_approved`
или вложение в вызов, остановка до сетевого запроса при критических и
неклассифицированных источниках, исключение для счетов, приоритет персональных
данных внутри счёта и скрытие содержимого в экспортируемом отчёте.

```sh
.venv/bin/python -m unittest discover -s tests -v
```

Новые реальные прогоны после смены политики нужны отдельно. Прежние успешные
прогоны подтверждают прежнюю версию, а не автоматически новую границу выдачи.
