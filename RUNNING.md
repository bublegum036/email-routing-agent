# Запуск проекта

Актуальная граница выдачи: [критические данные передаёт сотрудник](DATA_POLICY.md).
Автоматическая маршрутизация создаёт уведомление со ссылками и ручную проверку;
критическое содержимое не пересылается. Облачные вызовы на учебном наборе
разрешены благодаря явной метке `synthetic`; неизвестные/критические источники
останавливают облачную обработку. Счета на оплату исключены из категории
критического документооборота; персональные данные внутри них защищаются отдельно.

Требуется Python 3.11 или новее. В текущем окружении проверено на Python 3.13.
Внешних Python-зависимостей нет: используются `sqlite3`, `urllib` и `unittest`
из стандартной библиотеки. Все команды выполняются из корня проекта.
Оригинальное задание сохранено в [README.md](README.md).

## Изолированная среда Python

Для проекта создана `.venv`, исключённая из Git. Три варианта окружения:

| Вариант | Когда использовать |
|---|---|
| Базовый Python | Достаточен для текущего проекта без внешних зависимостей, но будущие пакеты не изолированы |
| `.venv` — рекомендуется | Отдельное окружение и пакеты для этого проекта |
| Контейнер Docker | Дополнительная изоляция системы, сейчас требует лишней настройки |

Для создания окружения на другом компьютере и активации:

```sh
python3 -m venv .venv
source .venv/bin/activate
```

В текущем проекте повторно создавать `.venv` не нужно. После активации команды
`python3` ниже используют её интерпретатор. Можно запускать его и явно:

```sh
.venv/bin/python -m unittest discover -s tests -v
.venv/bin/python -m email_router.doctor
.venv/bin/python -m email_router.smoke
```

Устанавливать зависимости для текущего кода не требуется. `venv` создаётся
на основе существующей установки Python и сама по себе не исправляет её
отсутствующий CA-файл. Если файл отсутствует, для Python 3.13 из python.org
используется штатный `Install Certificates.command`, описанный ниже.
При проверке созданной `.venv` CA-файл уже присутствовал; повторная установка
сертификатов без новой ошибки TLS не требуется.
Справка: [Python venv](https://docs.python.org/3.13/library/venv.html).

## Текущий провайдер: Google Gemini

Для подключения Gemini в `.env` подготовлено:

```dotenv
LLM_PROVIDER=gemini
LLM_MODEL=gemini-3.5-flash-lite
GEMINI_API_KEY=YOUR_LOCAL_GOOGLE_KEY
```

Создайте ключ на [странице Google AI Studio](https://aistudio.google.com/apikey)
для проекта **Free tier без подключённого биллинга** и вставьте его только
в локальный `.env`. Существующий ключ OpenRouter сохранён для возможного
возврата; Gemini его не использует. Переменные окружения имеют приоритет
над `.env`: если ранее экспортировались `LLM_PROVIDER`/`LLM_MODEL`, уберите
эти старые значения из текущего терминала перед запуском.

Рассмотрены три реализации: прямой REST Google, **совместимый интерфейс Chat
Completions (выбран)**, SDK `google-genai`. Совместимый endpoint позволяет
использовать существующие схемы инструментов и стандартную библиотеку Python.
Новые зависимости не требуются. Проверено по [совместимости API Google](https://ai.google.dev/gemini-api/docs/openai).

Для `gemini-3.5-flash-lite` документированы вызовы функций и бесплатный тариф:
[описание модели](https://ai.google.dev/gemini-api/docs/models/gemini-3.5-flash-lite),
[тарифы Google](https://ai.google.dev/gemini-api/docs/pricing).
В коде также допускается `gemini-3.1-flash-lite` как вручную выбираемая
альтернатива. Автоматической смены модели или провайдера нет.
В Gemini нет аналога нашего нулевого ограничения цены OpenRouter на запрос:
бесплатность определяется тарифом проекта Google. Проект с подключённым
биллингом может тарифицировать те же модели; код не определяет его тариф.
Включать биллинг для этого проекта не требуется.

После добавления ключа начните с одного короткого сценария:

```sh
.venv/bin/python -m email_router.smoke --mode workflow --message mail-02
```

Три объёма проверки: один workflow (меньше запросов); один агент
(`--mode agent --message mail-02`); полный прогон двух писем в обоих режимах
(команда `smoke` без аргументов). Каждая команда создаёт новую папку результатов.
Первый вариант проверяет подключение и извлечение вопроса одним обращением
к модели; он не заменяет проверку выбора инструментов агентом.

Параметры Gemini: `temperature=0`, `max_tokens=2400`, `reasoning_effort=low`.
Настройки и выбранный провайдер сохраняются в трассе. Служебные подписи
вызовов инструментов возвращаются Google без изменений.
Функциональные тесты адаптера используют подставной HTTP-ответ; реальное
подключение Gemini ещё требуется проверить после ввода ключа.

При проблемах с сетью используйте:

```sh
.venv/bin/python -m email_router.doctor --provider gemini
```

Этот вызов не читает ключ и не обращается к модели. HTTP 401/403 от Google
без авторизации означает, что DNS/TLS работают, но не подтверждает доступ
ключа, региона или модели. Лимиты проекта смотрите в Google AI Studio.
При выбранном Gemini команда `quota` выводит ссылку на его лимиты и не
использует OpenRouter. У сервиса есть [список доступных регионов](https://ai.google.dev/gemini-api/docs/available-regions);
фактическая доступность аккаунта/проекта подтверждается только подключением.

## Предыдущая настройка OpenRouter

Для возврата к OpenRouter укажите в локальном `.env`:

```dotenv
LLM_PROVIDER=openrouter
LLM_MODEL=nvidia/nemotron-3-super-120b-a12b:free
OPENROUTER_API_KEY=YOUR_LOCAL_KEY
```

Файл `.env` уже создан с пустым ключом и исключён из Git. Шаблон без секрета —
[.env.example](.env.example). Ключ создаётся на [странице ключей OpenRouter](https://openrouter.ai/settings/keys).
Не вставляйте ключ в код, аргументы команд, записи запуска или сообщения чата.
Переменные окружения имеют приоритет над `.env`.

Первоначально рассмотрены три бесплатных пути: OpenRouter, локальная модель
через Ollama и бесплатный тариф Gemini. Автор выбрал OpenRouter.
Адаптер теперь поддерживает OpenRouter, Gemini и локальный Ollama.
Пример локальной настройки оставлен в `.env.example` как альтернатива.

Для текущих повторных проверок закреплена
`nvidia/nemotron-3-super-120b-a12b:free` в локальной конфигурации и шаблоне.
Её [страница OpenRouter](https://openrouter.ai/nvidia/nemotron-3-super-120b-a12b:free)
подтверждает бесплатный endpoint и поддержку вызова инструментов. Это выбор
одного идентификатора модели, не обещание отсутствия ошибок или лимитов.

Первоначальный `openrouter/free` выбирает бесплатную модель с нужными возможностями. Он
может выбирать разные модели на разных запросах: фактическое имя и провайдер
сохраняются в каждом событии `model_response`. Это подходит для первого
подключения, но для итогового сравнения нужно выбрать конкретный доступный
идентификатор с суффиксом `:free` и записать его в `LLM_MODEL` для обоих режимов.
Наличие бесплатной модели и оставшаяся квота проверяются при реальном запуске;
первые реальные ответы через аккаунт получены, закреплённая модель после
последних изменений пока не проверена новым сетевым запуском.

При HTTP 429 сначала проверьте квоту без вызова модели:

```sh
.venv/bin/python -m email_router.quota
```

Команда читает `GET /api/v1/key` и выводит только числовые счётчики и лимиты;
ключ и название ключа не отображаются. `remaining=0` означает, что нужно дождаться
восстановления дневной квоты. Положительный остаток не исключает ограничения
по частоте или со стороны конкретного провайдера. Если API не вернул счётчик,
выводится неизвестный остаток, а не «безлимит». Smoke прекращает дальнейшие
запросы после HTTP 429, даже если до него в этом письме уже были ответы модели.
Он не обходит лимиты и не переключается на платные модели.

Клиент запрещает платные идентификаторы моделей, не задаёт платных fallback
и передаёт предельную цену 0 для входных/выходных токенов и запроса.
Ошибки квоты/доступности записываются, перехода на платную модель нет.
Сведения о бесплатном маршрутизаторе и параметре цены:
[Free Models Router](https://openrouter.ai/docs/guides/routing/routers/free-router),
[Provider Routing](https://openrouter.ai/docs/guides/routing/provider-selection).
Ограничения бесплатных запросов определяет аккаунт:
[Rate limits](https://openrouter.ai/docs/api/reference/limits).

В обоих режимах одна и та же настроенная модель: в workflow она выделяет
вопросы и ссылки, в агенте дополнительно выбирает инструменты. Параметры:
`temperature=0`, `max_tokens=2400`, без потоковой выдачи и скрытых повторов
клиента. Ограничения контроллера: до 16 обращений к модели, до 24 инструментов
основного цикла, 120 секунд на запуск с резервом завершения.
Качество этих настроек ещё предстоит измерить на реальной модели.

## Два реальных запуска агента

Для автоматического запуска обоих режимов на письмах 1 и 2:

```sh
python3 -m email_router.smoke
```

Команда создаёт новую папку `artifacts/live-check-...`, четыре независимые базы
и трассы, а также `summary.json` с проверкой получателей и сохранённых эффектов.
Если модель не ответила ни разу, дальнейшие запросы прекращаются. Неудачные
попытки сохраняются. При `openrouter/free` фактические модели могут различаться;
это начальная проверка реализации, а не окончательное сравнение архитектур.

Для двух разных путей:

```sh
python3 -m email_router run --mode agent --message mail-01 --db artifacts/live-agent-mail01.sqlite --output artifacts/live-agent-mail01.json
python3 -m email_router run --mode agent --message mail-02 --db artifacts/live-agent-mail02.sqlite --output artifacts/live-agent-mail02.json
```

Для workflow на тех же исходных данных:

```sh
python3 -m email_router run --mode workflow --message mail-01 --db artifacts/live-workflow-mail01.sqlite --output artifacts/live-workflow-mail01.json
python3 -m email_router run --mode workflow --message mail-02 --db artifacts/live-workflow-mail02.sqlite --output artifacts/live-workflow-mail02.json
```

Каждый новый файл базы получает одинаковые начальные данные. Для независимого
повторного эксперимента используйте новое имя базы и отчёта, чтобы сохранить
прежнюю попытку. Повтор команды с прежней базой имитирует повтор входящего
события: он восстанавливает прежний запуск и уже выполненные действия.
В одной базе нельзя переключать режим или модель существующего запуска.

Коды возврата: 0 — цикл завершён с квитанциями по всем вопросам; 1 — ошибка
запуска, в том числе ошибка модели с аварийной передачей человеку; 2 — неверная
конфигурация/команда. Код 0 сам по себе не доказывает правильность маршрута:
сверяйте результат с ожидаемым исходом сценария.

API-ключ не передаётся модели в тексте и не сохраняется в трассе. Формат
интеграции проверен по [Tool Calling OpenRouter](https://openrouter.ai/docs/guides/features/tool-calling).
Доступ к внешней сети нужен только для реального вызова модели.

Если выводится «Нет ответа модели», сначала проверьте соединение без ключа:

```sh
python3 -m email_router.doctor
```

Диагностика различает DNS, проверку сертификатов TLS, отказ соединения и
тайм-аут; выводит версию Python и наличие файла сертификатов. Она не читает
`.env`, не использует API-ключ и не выполняет запрос к модели.
Ошибка `TLS_CERTIFICATE` относится к доверенным сертификатам используемого
Python; отключение проверки HTTPS в проекте не применяется.

Для установленного с python.org Python 3.13 на macOS штатный установщик
сертификатов находится здесь (наличие файла на компьютере проверено):

```sh
bash "/Applications/Python 3.13/Install Certificates.command"
```

Дождитесь `update complete`, затем повторите `python3 -m email_router.doctor`.
Если `https` стал `OK`, запускайте `python3 -m email_router.smoke`.
Если установка завершилась ошибкой, сохраните её вывод. Проверка TLS остаётся
включённой. Это штатный шаг установки [Python на macOS](https://docs.python.org/3/using/mac.html).

## Как проверить фактическое действие

```sh
python3 -m email_router inspect --db artifacts/live-agent-mail02.sqlite
```

Команда показывает сохранённые заявки, исходящие сообщения и ручные передачи.
В JSON-трассе есть исходное письмо, зарегистрированные вопросы, запросы/ответы
модели, вызовы инструментов, наблюдения, квитанции и ошибки. В `outgoing`
проверяйте получателя, номер заявки и содержимое; в `actions` — идентификаторы
этих записей. Все адреса учебные; настоящие письма по SMTP не отправляются.

Пример ожидаемого результата на начальных данных:

| Письмо | Правильный результат |
|---|---|
| 1 | Через D-12 из истории — ответственному Марине, без обещания обслуживания |
| 2 | O-52 оплачен, не отгружен — обработке заказов |
| 3 | O-51 отгружен — логистике |
| 4 | Дополнить T-9 и уведомить текущего исполнителя Сергея; не создавать вторую заявку |
| 5 | Передать согласие на пять комплектов продажам C-11 без создания коммерческого заказа |
| 6 | Уточнить принадлежность компании/детали или обоснованно передать сотруднику |
| 7 | Отдельно передать пять комплектов продажам и задержку O-52 обработке заказов |
| 8 | Ручной разбор; без чтения договора и без внешней отправки |

Эти ожидания предполагают исходные записи из `data/seed.json` и отсутствие
добавленных заявок по тем же вопросам. В повторных событиях используется
уже изменённое состояние, а не повторно загруженная исходная база.

## Проверка без API-ключа

```sh
python3 -m unittest discover -s tests -v
python3 -m email_router demo --directory artifacts/offline-demo
python3 -m email_router inspect --db artifacts/offline-demo/agent/mail-02/state.sqlite
```

`demo` использует **заранее заданные сценарии вместо языковой модели**.
Он проверяет выполнение контроллера и сохранение эффектов, но не способность
модели понимать письма, выбирать инструменты, экономить токены или превосходить
workflow. Метка `live_model=false` есть и в выводе, и в файлах трасс.
Не включайте эти прогоны в результаты реального сравнения из шага 6.

`demo_model.py` понимает только восемь исходных разработческих писем; это
тестовая подстановка, не запасной режим при недоступности OpenRouter.
Реальный запуск никогда автоматически не переключается на неё.

## Текущие ограничения

Модель может пропустить намерение или неверно понять связь двух вопросов.
Проверки формата и разрешений не доказывают правильность смысла. Для повторных
обращений без точной связи используем осторожный поиск: несколько подходящих
заявок дают неоднозначность и ручной разбор. Не гарантируем полноту поиска
по произвольным формулировкам естественного языка.

Локальное подтверждение отправителя — запись учебного реестра, не настоящая
аутентификация почты. Нет обработки вложений, SMTP, фонового ожидания ответов
и нескольких конкурентных рабочих процессов. Данные и исходящие сообщения
сохраняются в одной SQLite-базе; это намеренная граница стенда.

В первой реализации при обнаружении нового намерения после регистрации
вопросов нужно передать исходное письмо сотруднику; автоматическое изменение
разбиения после частичного исполнения не реализовано. Полноту исходного
разбиения проверяет набор ожиданий. Лимиты и качество реального tool calling
надо подтвердить после подключения OpenRouter.

## Регрессия после изменения промпта, модели или инструментов

```sh
.venv/bin/python -m email_router.regression --offline --with-unit-tests
```

Реальный Gemini-прогон: `.venv/bin/python -m email_router.regression --mode workflow`.
17 кейсов, три повтора, отдельное состояние каждой попытки; для agent указать
`--mode agent`, для обоих — `--mode both`. Ожидания, сравнение версий,
продолжение после ошибки API и ограничения метрик описаны в [STEP8.md](STEP8.md).
Реальный workflow-прогон подтверждён: 51/51 попытки, по три для 17 кейсов.
Шаг 8 для workflow завершён реальным сравнением runtime: 48/51 до, 51/51
после, регрессий нет. Полный agent-прогон остаётся отдельной проверкой;
offline не подтверждает качество модели.
