# Полный пример: ошибка → исправление → повторная проверка

Это фактическая ошибка извлечения аргументов и обработки отказа в workflow,
одном из двух сравниваемых режимов. Это не сетевая ошибка и не случай,
в котором модель правильно передала действительно неопределённое письмо человеку.
Исправление ранее внесено в общий контроллер; сейчас повторно проверено.

## Письмо и правильный результат

Исходное `mail-02` от зарегистрированного Олега:

> По заказу O-52 деньги ушли неделю назад. Когда получим оборудование?

Учебный реестр связывает отправителя с C-21. Источник заказа O-52 указывает:
оплачен, не отгружен. Поэтому нужно проверить существующие обращения и
назначить новый вопрос обработке заказов, `order_operations`.
Утверждение письма об оплате само по себе не является подтверждением.
Нельзя придумывать срок доставки, менять заказ или создавать дубли.

## 1. Реальная неудачная попытка

Сохранённая трасса:
[workflow-mail-02.json](artifacts/live-check-20261016T211218292603Z/workflow-mail-02.json).

Модель извлекла:

```json
{
  "category": "order",
  "company_hint": "customer.example.test",
  "reference_id": "mail-02"
}
```

`customer.example.test` — домен отправителя, а не название компании из письма.
`mail-02` — идентификатор сообщения, а не номер заказа.
Инструмент не принял неподтверждённые параметры. Workflow дополнительно
ошибся при обработке отказа: назвал ошибку аргументов `source_unavailable`.
Сохранились `human_review` и ручной разбор вместо правильного назначения.
Сеть и источник заказа в этой попытке не были недоступны.

Причины находятся на двух границах: модель неверно извлекла параметры,
а контроллер не проверил их происхождение и неверно классифицировал отказ.

## 2. Исправление

В [email_router/runner.py](email_router/runner.py) добавлена `ground_hints`:

- Подсказка компании должна присутствовать в письме или уже прочитанной истории.
- Номер должен иметь вид D-/O-/T-номер и присутствовать в доступном тексте.
- Если в точной цитате вопроса есть ровно один такой номер, он восстанавливается
  из цитаты. При нескольких номерах выбирать первый запрещено.
- Идентификацию и полномочия по-прежнему проверяет `resolve_customer`.
- Ошибки параметров отделены от недоступности источника.

Для этого ответа результат проверки:

```json
{
  "before": {
    "company_hint": "customer.example.test",
    "reference_id": "mail-02"
  },
  "after": {
    "company_hint": "",
    "reference_id": "O-52"
  }
}
```

Это извлечение явно указанного номера, а не догадка о компании.
Исходный ответ модели не переписывается; изменение фиксируется отдельным
событием `extraction_correction`. Описания параметров в инструкции также уточнены.

## 3. Тот же ответ после исправления

Повтор от 19 октября:
[summary.json](artifacts/error-example-replay-20261019T181400915817Z/summary.json),
[trace.json](artifacts/error-example-replay-20261019T181400915817Z/trace.json).

В чистую базу загружен исходный стенд. Из реальной неудачной трассы взято
полное сообщение модели; оно подано текущему workflow без изменения.
Сохранённый `model_response.message` в повторе равен историческому сообщению.
Ожидания и хеш исторической трассы сохранены до обработки.

Получено:

1. Подтверждённый клиент C-21.
2. Успешное чтение O-52 с фактическими статусами источника.
3. Проверка существующих заявок.
4. Одна новая заявка и назначение `order_operations`.
5. Одно фиксированное служебное уведомление без клиентского содержимого;
   передача содержимого требует проверки сотрудника.

Итог: `routed`, правильный получатель, лишних эффектов нет.
`live_model=false`: это воспроизведение ответа, не новый вызов модели
и не измерение качества или токенов LLM. Исторический файл не изменён.
Проверка использует текущую систему целиком; отдельный эксперимент с отключением
всех остальных изменений с даты исходной попытки не проводился.

## 4. Автотест и обычное письмо с реальной моделью

Регрессионный тест содержит точные ошибочные аргументы исходной попытки
и проверяет правильный маршрут, исправленные поля и событие коррекции.
Команда из корня проекта:

```sh
PYTHONPATH=tests .venv/bin/python -m unittest \
  test_router.ControllerTests.test_real_failed_extraction_is_recovered_from_explicit_order_number -v
```

Тест прошёл. Все текущие 58 автотестов также прошли.

То же обычное письмо отдельно успешно обработано с Gemini в чистой базе:
[normal_order.json](artifacts/live-recovery-20261019T180958361346Z/normal_order.json).
Это реальный запуск: `get_order → found`, одна новая заявка, получатель
`order_operations`, одна проверка содержимого сотрудником.
Ранее workflow с Gemini также успешно обработал его в сравнении:
[workflow-mail-02.json](artifacts/live-comparison-20261016T223012500365Z/workflow-mail-02.json).

Модели исторической ошибки и новых реальных запусков различаются.
Поэтому успешный Gemini-запуск подтверждает работу текущей системы,
но не изолирует эффект исправления на старой модели. Регрессию конкретного
ошибочного ответа показывает именно воспроизведение того же сообщения.

## Что объяснить на защите

«Модель спутала номер письма с номером заказа и использовала домен как компанию.
Наш контроллер вдобавок неверно назвал ошибку параметров недоступностью источника.
Мы проверили происхождение полей и разделили причины отказа. На том же сохранённом
ответе в чистой базе теперь получается правильный маршрут. Обычное письмо с
реальной моделью тоже прошло. Это не отменяет остальных ошибок понимания:
при нескольких номерах и неясной связи нельзя автоматически выбирать один».

Этот пример даёт свидетельства фактической ошибки, исправления и повторной
проверки. Он не является новым экспериментом усложнения до границы неудачи:
отдельное требование шага 5 не нужно подменять этим историческим случаем.
