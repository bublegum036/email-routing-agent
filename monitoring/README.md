# Локальный мониторинг email router

Prometheus + Grafana + сборщик числовых метрик из регрессионных сводок.
Это наблюдение учебных запусков: работа с настоящей почтой, измерение ручной
очереди и уведомления во внешние каналы здесь не включены.

## Запуск

Открой Docker Desktop, дождись готовности движка. Из корня проекта:

```sh
.venv/bin/python monitoring/manage.py up
```

Команда создаёт локальный пароль Grafana, проверяет Compose, собирает сборщик,
запускает контейнеры и проверяет HTTP, источник данных и scrape Prometheus.
Первые образы скачиваются через Docker. Контейнеры используют отдельную
bridge-сеть проекта; публикация портов только на 127.0.0.1. Исходящая сеть
технически доступна контейнерам. Отправка метрик и уведомлений наружу не настроена;
изолированной от исходящей сети эту конфигурацию считать нельзя.
Модель Gemini не вызывается, новые эксперименты не запускаются.

| Адрес | Что открыть |
|---|---|
| http://localhost:13000/d/email-router-local | Готовая панель Grafana |
| http://localhost:19090/targets | Проверка опроса сборщика |
| http://localhost:19090/alerts | Локальные тревоги |
| http://localhost:19108/metrics | Только обезличенные метрики |

Панель доступна локально с правами Viewer без входа. Для административного
входа логин `admin`, пароль — в `monitoring/local/grafana_admin_password`.
Открой файл локально при необходимости. Значение не выводится командой запуска
и не попадает в Git. Каталог закрыт для других пользователей macOS;
доступность самого файла внутри контейнера нужна процессу Grafana.
При повторном запуске пароль не заменяется. Если уже существует том Grafana,
начальная настройка пароля не сбрасывает пароль существующего администратора.

Проверка и остановка:

```sh
.venv/bin/python monitoring/manage.py status
.venv/bin/python monitoring/manage.py check
.venv/bin/python monitoring/manage.py down
```

Если контейнеры запущены, но готовность не подтверждена, команда check выводит
пять отдельных проверок: exporter_http, current_source, prometheus_http,
grafana_database и prometheus_scrape. Для ошибки HTTP выводится только статус;
отказ соединения, сброс, таймаут и запрет доступа имеют отдельные reason.
Тела ответов и тексты исключений не печатаются. Точная причина недоступности
сети определяется после получения этой диагностики на Mac. Контейнеры при
неуспехе проверки остаются запущенными, существующие данные сохраняются.

Остановка сохраняет именованные тома с историей Prometheus и состоянием Grafana.
Автоматически удалять тома или сбрасывать их содержимое команда не будет.
Порты 13000, 19090 и 19108 должны быть свободны; их можно изменить в Compose
вместе с адресами проверки в manage.py и ссылками панели.

## Что показывает панель

В `sources.json` настроены два независимых источника:

- `current`: сначала выбирается последний каталог live-regression-<UTC timestamp>,
  затем читается его summary.json. Новая папка без сводки, повреждённый файл
  или недопустимая символическая ссылка дают source_loaded=0. Отката к старому
  успешному прогону нет. После появления корректной сводки метрики восстанавливаются
  на следующем опросе.
- `baseline`: сохранённый старый workflow `step8-workflow-before-final`.
  Его три известных неуспеха показываются отдельно и не вызывают текущих тревог.

Режимы workflow и agent разделены. Пока выбранный прогон не содержит agent,
для него нет данных. Offline-папки никогда не выбираются как current. При
необходимости добавь в sources.json именованный источник с role=offline и
directory, указывающим на отдельный offline-прогон, затем перезапусти exporter.
Для дополнительного источника нужно добавить его ID в переменную source панели.
В текущем источнике должно оставаться имя current для команды проверки.

Метрики вычисляются из checks, поле aggregate не используется. Есть число
попыток, правильных и неправильных исходов, незавершённых и ещё не запущенных
слотов; известные вызовы/токены и неизвестный расход; время с паузами,
маршрутизации и ручные передачи, блокировки, повторы и нарушения содержимого.
pass@3/pass^3 отсутствуют, пока не получены все три попытки каждого кейса.
Графики являются снимками набора; это gauge, а не монотонные счётчики.
При выборе следующего прогона значения могут уменьшиться: rate() для них
использовать нельзя. Сводки продолжений читаются как один набор checks,
без повторного сканирования трасс предыдущих папок.

Возраст снимка — возраст учебного эксперимента, не задержка рабочего письма.
Стенд запускается вручную, поэтому отсутствие нового эксперимента не вызывает
тревогу о якобы зависшей рабочей очереди. Достоверную оценку реальной ошибки
маршрута даст только эталон или проверка сотрудника; сейчас это эталоны шага 8.
Токены — известная сумма; null или неполный usage учитывается отдельно.
Критическая граница с нулём вызовов не считается неизвестным расходом API.

## Локальные тревоги

Правила Prometheus проверяются каждые 15 секунд:

| Сигнал | Выдержка | Действие |
|---|---:|---|
| Сборщик не отвечает | 1 мин | Проверить контейнер exporter |
| Текущий источник не загружается | 1 мин | Проверить новый summary и sources.json |
| Завершённая неуспешная попытка | 30 с | Разобрать локальную трассу текущего прогона |
| Запрещённое содержимое по проверяющему коду | Без выдержки | Остановить автоматическую обработку, передать разбор сотруднику |
| Незавершённая попытка | 5 мин | Проверить прерывание, API и сохранённую базу |
| Остановка по бюджету | 30 с | Проверить лимиты и траекторию |

Тревоги — в Prometheus /alerts и панели Grafana. Внешние получатели, SMTP,
Telegram, webhook и автоматический откат не настроены. Канал уведомлений
подключается отдельным согласованным изменением. На время сна Mac наблюдение
не работает; накопившиеся данные не означают круглосуточного наблюдения.

## Граница данных

Сборщик читает только summary.json выбранных каталогов. Он не открывает
SQLite, исходные письма, JSON/JSONL-трассы или .env. Каталог artifacts подключён
только для чтения. Из summaries разрешены только ограниченный набор чисел,
режим agent/workflow и признак live/offline. Метки source и role берутся из
проверенной локальной конфигурации: произвольные строки отчёта в метки не идут.
Никаких клиентских ID, адресов, текста, резюме или тел ошибок в /metrics нет.
Повреждение источника даёт source_loaded=0 без частичной публикации метрик
этого источника и без выдачи содержимого ошибки. Для каждой завершённой
попытки обязательны все разрешённые диагностические поля, включая
forbidden_content_effects. Отсутствие даже одного поля означает ошибку источника;
нулевые нарушения вместо отсутствующей диагностики не публикуются.
У начатой, но незавершённой попытки диагностика может быть неполной: это
отмечается incomplete и unknown_diagnostics_attempts, отдельно показанными
на панели. Суммы диагностик такого прогона относятся только к известным данным.

Контекст Docker-сборки — только monitoring, .dockerignore разрешает лишь
Dockerfile и exporter.py. Файлы проекта, API-ключи и локальный пароль не
копируются в образ. Compose использует отдельный пустой compose.env, поэтому
проектный .env не подставляется в конфигурацию. Настройка Prometheus не содержит
remote_write, Alertmanager или отправку метрик во внешнюю систему.

## Версии и проверки

Prometheus 3.13.4 LTS и Grafana OSS 13.2.4 зафиксированы по официальным страницам
на момент настройки; Python-образ ограничен веткой 3.13-slim. Его точный digest
зависит от момента первой загрузки. Пользовательские плагины не устанавливаются.
Источники: [Prometheus](https://prometheus.io/download/),
[Grafana](https://grafana.com/grafana/download?edition=oss),
[provisioning Grafana](https://grafana.com/docs/grafana/latest/administration/provisioning/).

Локальная проверка проекции без Docker:

```sh
.venv/bin/python monitoring/exporter.py --artifacts artifacts --config monitoring/sources.json --once
.venv/bin/python -m unittest discover -s tests -v
```

Для проверки правил настоящим promtool после сборки/загрузки образов:

```sh
docker compose --env-file monitoring/compose.env -f compose.monitoring.yaml run --rm --no-deps --entrypoint /bin/promtool prometheus check config /etc/prometheus/prometheus.json
```

В среде Codex Docker CLI установлен, но доступ к Docker socket запрещён;
привязка локального HTTP-порта также запрещена. Здесь проверены проекция,
отрицательные сценарии, обработчики HTTP без сетевого сокета и Compose config.
Пользователь подтвердил фактический запуск на Mac 20 октября 2026 после
пересоздания сети как bridge: все три контейнера Healthy, команда up вывела
OK для exporter, live source, Prometheus scrape и Grafana. Для образа сборщика
использован python:3.13-slim с digest
sha256:70729b46c69b4f1e97c4822c1af3df53a1476cf5ddc6c087c0c10bc3a5678c2f.
115 автотестов прошли; Compose config проверен. Отображение панелей в браузере
и отдельная команда promtool этим выводом ещё не подтверждены.

### После первоначального запуска с internal-сетью

Первоначальная конфигурация использовала internal: true. На Docker Desktop это
может мешать доступу к опубликованным портам с Mac, хотя сервисы внутри Docker
работают. Конфигурация изменена на bridge с портами только на 127.0.0.1.
Для применения нужно пересоздать сеть, сохранив тома:

```sh
.venv/bin/python monitoring/manage.py down
.venv/bin/python monitoring/manage.py up
```

Команда down вызывается без -v: базы Grafana и Prometheus и локальный пароль
сохраняются. После up все проверки должны пройти. Если остаётся ошибка,
нужен вывод check с уточнённым reason и status. Работоспособность на конкретном
Docker Desktop подтверждается после этого перезапуска, а не только тестами.

После исправления двух замечаний ревью прошли 119 автотестов. Отрицательные
проверки покрывают новую папку без сводки, последующее восстановление, отсутствие
каждого обязательного поля диагностики и недопустимую ссылку вместо нового запуска.
Текущий и baseline-источники повторно проверены локальной числовой проекцией.
Для применения изменений к работающему сборщику повторить команду up.
